# Terraform Workspace — Civo Cloud

A hands-on **Terraform + Civo Cloud** project demonstrating reusable modules, Terraform Workspaces, environment isolation, remote state, and Infrastructure as Code best practices.

> **Project goal:** provision repeatable development and production infrastructure from the same Terraform configuration while keeping each environment isolated through Terraform Workspaces.

## Architecture

```text
                         Terraform Root Module
                                  │
              ┌───────────────────┼───────────────────┐
              │                   │                   │
              ▼                   ▼                   ▼
       Network Module       Firewall Module      Instance Module
              │                   │                   │
              │                   │              ┌────┴────┐
              │                   │              │         │
              ▼                   ▼              ▼         ▼
       Civo Network          Civo Firewall   Instance 1  Instance 2
              │                   │              │         │
              └──────────────┬────┴──────────────┴─────────┘
                             │
                      Terraform Workspace
                       dev / prod isolation
                             │
                             ▼
                    Civo Object Store Backend
                         Remote State (S3)
```

Each workspace creates its own network, firewall, and **two Civo instances**. Resource names include `terraform.workspace` so `dev` and `prod` can coexist without naming collisions.

## Project Highlights

- Reusable Terraform modules for network, firewall, and compute resources.
- Terraform Workspaces for `dev` and `prod` state isolation.
- Workspace-aware resource naming.
- Two Civo instances per workspace using Terraform `count`.
- Explicit module inputs and outputs for resource dependencies.
- Civo Object Store used as an S3-compatible remote Terraform backend.
- Credentials kept outside the repository through environment variables and GitHub Secrets.
- Terraform formatting, validation, and plan checks through GitHub Actions.

## Terraform Configuration

The project requires Terraform `>= 1.15.0` and uses the Civo provider with the `~> 1.1` version constraint.

### Root variables

| Variable | Description | Example |
|---|---|---|
| `region` | Civo region | `nyc1` |
| `ssh_key_id` | Civo SSH key ID | `YOUR_SSH_KEY_ID` |
| `disk_image` | Civo disk image UUID | `YOUR_DISK_IMAGE_UUID` |

`network_id` and `firewall_id` are generated by modules and passed to the instance module; they are not root input variables.

## Terraform Workspaces

The project uses Terraform Workspaces to maintain separate state for each environment:

```text
                    Terraform Configuration
                              │
                 ┌────────────┴────────────┐
                 │                         │
                dev                       prod
                 │                         │
        ┌────────┼────────┐        ┌───────┼────────┐
        ▼        ▼        ▼        ▼       ▼        ▼
      Network Firewall Instances Network Firewall Instances
                         (2)                    (2)
```

### Development

```text
dev
├── devops-dev-network
├── devops-dev-firewall
├── cloudops-dev-1
└── cloudops-dev-2
```

### Production

```text
prod
├── devops-prod-network
├── devops-prod-firewall
├── cloudops-prod-1
└── cloudops-prod-2
```

The same Terraform code is used for both environments. The workspace name is injected into resource names through `terraform.workspace`.

## Remote Terraform State

The project uses **Civo Object Store** as an S3-compatible remote backend.

Backend endpoint:

```text
https://objectstore.nyc1.civo.com
```

The backend is configured in `backend.tf`:

```hcl
terraform {
  backend "s3" {
    bucket = "terraform-state"
    key    = "terraform.tfstate"

    endpoints = {
      s3 = "https://objectstore.nyc1.civo.com"
    }

    region = "nyc1"

    skip_credentials_validation = true
    skip_requesting_account_id  = true
    skip_region_validation      = true
    skip_metadata_api_check     = true
    use_path_style              = true
    skip_s3_checksum            = true
  }
}
```

The backend uses the S3 protocol for compatibility, but the actual object storage is **Civo Object Store**, not AWS S3.

### Backend credentials

Never commit Object Store credentials to Git.

Configure them through environment variables:

```bash
export AWS_ACCESS_KEY_ID="YOUR_CIVO_OBJECT_STORE_ACCESS_KEY"
export AWS_SECRET_ACCESS_KEY="YOUR_CIVO_OBJECT_STORE_SECRET_KEY"
```

These variable names are used because Civo Object Store provides an S3-compatible API.

## Getting Started

### 1. Clone the repository

```bash
git clone https://github.com/n00shy/terraform-workspace.git
cd terraform-workspace
```

### 2. Configure credentials

Configure your Civo API credentials using your preferred secure method. For local development, use the Civo CLI or environment variables.

Do not commit API tokens or Object Store credentials.

### 3. Create `terraform.tfvars`

Create a local `terraform.tfvars` file:

```hcl
region     = "nyc1"
ssh_key_id = "YOUR_SSH_KEY_ID"
disk_image = "YOUR_DISK_IMAGE_UUID"
```

`terraform.tfvars` is intentionally ignored by Git.

### 4. Initialize Terraform

```bash
terraform init
```

### 5. Format and validate

```bash
terraform fmt -recursive
terraform validate
```

### 6. Create the development workspace

```bash
terraform workspace new dev
```

If it already exists:

```bash
terraform workspace select dev
```

### 7. Plan and apply development

```bash
terraform plan
terraform apply
```

This provisions one network, one firewall, and two Civo instances for `dev`.

### 8. Create production

```bash
terraform workspace new prod
```

Or select the existing workspace:

```bash
terraform workspace select prod
```

Then:

```bash
terraform plan
terraform apply
```

This provisions a separate production network, firewall, and two instances with separate workspace state.

## Workspace Commands

List all workspaces:

```bash
terraform workspace list
```

Show the current workspace:

```bash
terraform workspace show
```

Switch environments:

```bash
terraform workspace select dev
terraform workspace select prod
```

### Destroy an environment

Terraform destroy affects the **currently selected workspace only**:

```bash
terraform workspace show
terraform destroy
```

> Always verify the active workspace before running `terraform destroy`, especially when working with `prod`.

## Outputs

The root module exposes:

- `network_id`
- `firewall_id`
- `instance_ids`
- `instance_public_ips`

The instance outputs use `module.instance[*]` because the instance module is created multiple times with Terraform `count`.

## CI/CD

The repository includes a GitHub Actions workflow for automated Terraform checks on pushes and pull requests targeting `main`.

The workflow runs:

```bash
terraform fmt -check -recursive
terraform init -reconfigure
terraform workspace select -or-create dev
terraform validate
terraform plan
```

The workflow intentionally stops at **plan**. It does not run `terraform apply`, preventing a repository push or pull request from automatically changing cloud infrastructure.

Sensitive values such as the Civo API token and remote backend credentials should be provided through **GitHub Secrets**, never hard-coded in workflow files or Terraform configuration.

## Security

Sensitive infrastructure data is intentionally excluded from Git.

The `.gitignore` protects files such as:

```text
terraform.tfvars
terraform.tfstate
terraform.tfstate.*
.terraform/
*.pem
*.key
```

Never commit:

- Civo API tokens
- Civo Object Store access keys
- Terraform state containing sensitive data
- SSH private keys
- Environment-specific secrets

If a secret is ever committed accidentally, rotate/revoke it immediately and remove it from Git history where appropriate.
